<!-- section: goal-rationale -->
## Goal and rationale

Projects consuming generated OCCT bindings receive compile-time errors when handwritten code uses
public Runtime entry points that exist only so generated wrapper implementations can cross an
assembly boundary. The Runtime analyzer enforces this narrow caller-usage policy without becoming
an ownership analyzer, a declaration authority, or a runtime security boundary.

<!-- section: scope -->
## Scope and non-goals

- In scope: a separate `TedToolkit.Occt.Runtime.Analyzers` compiler asset; the public
  `TedToolkit.Occt.Runtime.GeneratedCodeOnlyAttribute` metadata contract that marks an unavoidable
  public member as reserved for generated code;
  deterministic distinction between generated and handwritten call sites; stable error
  diagnostics; focused analyzer tests; clean-build and package wiring; and consumer guidance.
- In scope: every relevant symbol-use form, including explicit and target-typed construction,
  invocation, property or event access, and method-group or delegate capture. The first required
  case is handwritten construction through
  `Handle<T>(T* value, delegate* unmanaged[Cdecl]<T*, void> release)`.
- In scope when their owning changes introduce them: generated-only `Owned<T>` admission,
  construction, lease, or address entry points and unavoidable public module, fingerprint, native
  invocation, or cleanup hooks. The same metadata-driven rule covers them without a
  declaration-specific allowlist or one analyzer per API.
- Preserved: generated factories and operations; `Handle<T>.Dispose()`; non-owning data access
  through `Handle<T>.Value`; ordinary exception, metadata, and wrapper-author contracts; and
  independently produced generated wrappers.
- Non-goals: diagnosing `IDisposable` on exact-layout structs; general owner leak, disposal, alias,
  or transfer analysis; banning ordinary struct construction; diagnosing routine operations
  through `.Value` when the generated receiver types already make them unavailable; code fixes;
  reflection or `dynamic`; or renaming the existing source-generator project.
- Compatibility: no Runtime analyzer, reserved-use metadata, or stable diagnostic IDs have been
  released. Analyzer diagnostics are suppressible and cannot establish trustworthy caller
  identity, so API shape and Runtime validation remain authoritative.

## Behavior contract

| ID | Observable boundary | Current | Expected | Preserved |
| --- | --- | --- | --- | --- |
| OB-01 | Raw Handle construction | Any unsafe caller can invoke the current public constructor | A handwritten constructor use reports an error; generated wrapper construction is accepted | The constructor remains public for cross-assembly generated integration |
| OB-02 | Reserved Runtime hooks | Public implementation hooks have no common usage policy | Any handwritten operational reference to marked Runtime API reports `TTOCCT001` as an error | Unmarked public APIs remain ordinary contracts |
| OB-03 | Generated callers | Caller recognition is undefined | Code classified as generated by the Roslyn analyzer driver may use marked APIs without assembly-name or friend-access privilege | Independent generators can target Runtime |
| OB-04 | Tooling boundary | The existing Analyzer is an OCCT-header source generator | Runtime usage diagnostics build and ship as a separate compiler asset with no runtime dependency | Existing source generation and generator validation are unchanged |
| OB-05 | Enforcement boundary | Public hooks are callable if the analyzer is absent or suppressed | Runtime still validates type, pointer, module, ownership, and disposed-state invariants before native access | The analyzer is developer guidance, not authorization |

<!-- acceptance-case: AC-01 -->
### AC-01 — Handwritten code cannot construct Handle directly by default

```gherkin
Scenario: Construct a Handle from handwritten code
  Given the public raw-pointer Handle constructor is marked for generated code only
  When handwritten code uses explicit or target-typed object creation
  Then the Runtime analyzer reports TTOCCT001 on the constructor use
  And the diagnostic directs the caller to a generated factory or operation
```

<!-- acceptance-case: AC-02 -->
### AC-02 — One rule covers every reserved Runtime API use

```gherkin
Scenario: Reference marked Runtime implementation hooks
  Given marked constructors, methods, properties, events, and capturable methods
  When handwritten code invokes, accesses, subscribes, or captures them
  Then every operational reference reports TTOCCT001
  And unmarked Runtime and generated binding APIs remain diagnostic-free
```

### AC-03 — Generated wrappers use the same public contracts

```gherkin
Scenario: Compile independently generated wrappers
  Given two generated wrapper assemblies use Roslyn's standard generated-code classification
  When they construct owners and invoke marked Runtime hooks
  Then neither receives a reserved-API diagnostic
  And neither needs an assembly-name allowlist, InternalsVisibleTo, reflection, or private access
```

### AC-04 — Safe consumer behavior remains available

```gherkin
Scenario: Consume generated bindings normally
  Given handwritten code uses generated factories and operations, Handle.Dispose, and Value data access
  When the Runtime analyzer runs
  Then no Runtime analyzer diagnostic is reported
  And exact-layout structs are not subjected to Runtime disposal or owner-flow diagnostics
```

<!-- acceptance-case: AC-05 -->
### AC-05 — Runtime analyzers ship only as compiler assets

```gherkin
Scenario: Compile a package consumer from a clean build
  Given a supported Runtime or generated binding package reference
  When the consumer compiles
  Then exactly one Runtime analyzer assembly participates in compilation
  And no analyzer assembly or analyzer implementation dependency becomes a runtime dependency
```

## Constraints and risks

- [GEN-03](../../principles/README.md#gen-03-separate-native-representation-from-ownership-and-behavior),
  [GEN-04](../../principles/README.md#gen-04-keep-the-shared-runtime-minimal-and-declaration-agnostic),
  and the [generated binding architecture](../../architecture/generated-binding-system.md) govern
  this change. The active [Runtime analyzer boundary](../../architecture/runtime-analyzer-boundary.md)
  supplies the detailed contract.
- Access modifiers and type shape come first. A reserved-use marker is allowed only when a
  generated implementation must call a cross-assembly API that cannot be less visible.
- The public marker is sealed
  `TedToolkit.Occt.Runtime.GeneratedCodeOnlyAttribute`, applicable once to constructors, methods,
  properties, and events without inheritance. The analyzer also honors the marker on an associated
  accessor when Roslyn binds consumer syntax to that accessor.
- The first diagnostic is `TTOCCT001`, enabled by default with error severity and the
  message that the referenced API is reserved for generated OCCT binding code.
- Runtime owns the marker contract but does not depend on the analyzer. The analyzer recognizes
  symbols by metadata contract and must not contain OCCT declaration names, generated package
  identities, wrapper assembly names, or native symbols.
- The analyzer configures `GeneratedCodeAnalysisFlags.None` and therefore relies on the Roslyn
  analyzer driver's generated-code classification. Source-generator output and independently
  generated files following standard generated-file names, headers, or `generated_code = true`
  configuration receive the same exemption. This is not proof of trust; users can configure or
  imitate generated code and can suppress diagnostics.
- The `TedToolkit.Occt.Runtime.Analyzers` package contains no runtime assets and supplies
  its analyzer through `buildTransitive`. The Runtime package depends on it; generated binding
  packages depend on Runtime and do not embed or reference a second analyzer copy.
- Escalate if correctness depends on the diagnostic being unsuppressible, if trusted caller
  identity is required, or if a supposedly reserved API can instead be private, internal, or
  expressed through a safe public abstraction.

## Delivery brief

- Outcome: add the metadata-driven reserved-API analyzer, generated-caller recognition, tests,
  stable diagnostics, package wiring, and consumer documentation; apply the marker to the completed
  Handle constructor and cover other approved generated-only Runtime hooks introduced by their
  owning changes.

  remaining hook inventory is confirmed during preflight.

  `tests/TedToolkit.Occt.Runtime.Analyzers.Tests`, Runtime metadata, generated wrapper emission,
  solution ordering, and package assets.
- Private choices left open: analyzer callback and operation model, metadata symbol lookup,
  generated-tree detection implementation, diagnostic implementation types, and fixture layout.

## Completion

`TTOCCT001`; generated wrappers and safe consumer APIs remain diagnostic-free; no Runtime

the analyzer has no declaration or wrapper allowlist; and exactly one analyzer compiler asset ships
